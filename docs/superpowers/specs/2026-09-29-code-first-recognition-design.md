# Code-first recognition, learning loop, and ML showcase

Status: approved design, 2026-09-29.

## Goal

Scan any One Piece TCG card and identify its exact printing: read the card code, list every printing
that shares it, and let an on-device vision model pick the right one. Accuracy improves over time from
real scans labeled in the app, and the whole process becomes an ML project to showcase: model cards,
an accuracy-over-time chart, a demo video, and a live results page.

## Decisions

| Topic | Decision |
| --- | --- |
| Pipeline order | Code first (OCR), vision picks within the code's printings; vision-only fallback when OCR fails |
| Card scope | Any card in the full OPTCG catalog (~4k printings). Roster cards spawn a character; others show a card-info panel |
| Models | Local only. On-device Core ML embedder (MobileNetV3, fine-tuned). Apple Vision OCR, measured but not trained. No cloud models. A local VLM labeling helper is out of scope for now |
| Labels | Explicit confirm/correct taps in the app. Unlabeled scans are never used for training or testing |
| Split | By printing ID (stable hash), 30% test. A test printing never contributes a real scan to training |
| Test set | Frozen as `test-vN` at ≥200 scans across ≥30 printings. All metrics reported with 95% confidence intervals |
| Machines | MacBook = iOS dev and app builds. Mac mini = datasets, training, evals, showcase generation |
| Transport | iPhone → Mac mini over SMB (Files app). Mac mini → MacBook binaries over rsync/SSH. Text artifacts over git |
| Results page | Generated static site pushed to a separate public repo, `op-tcg-ar-results` (main repo stays private) |

## 1. Recognition flow (phone and `cardvision` CLI)

`CardRecognizer` implements the flow once, in the `CardVision` target, so the CLI evaluation keeps
measuring exactly what the phone runs.

1. **Detect and rectify** to the canonical 630×880 card. Unchanged.
2. **Read the code.** `CardOCR` on the upright crop. If no valid code is parsed, OCR the 180°-rotated
   crop. The orientation that produced a code becomes the working orientation.
3. **Look up the group.** `FullCatalog.printings(forCode:)` returns every printing with that code.
4. **Pick the printing.**
   - Group of 1: the result is that printing, with no embedding step. `method = ocr-unique`.
   - Group of ≥2: embed the crop and rank only the group's index rows (`EmbeddingIndex` restricted
     search). All group members are returned, ranked. `method = ocr+vision`.
   - An OCR code that isn't in the catalog is treated as an OCR failure.
5. **Fallback.** No code in either orientation: embed both orientations, search the full catalog index,
   return the top 5 for the better orientation. `method = vision-only`. If the best similarity is below
   `minimumSimilarity`, return `nil` ("not a card") and keep scanning.

`RecognitionResult` gains `method`, `ocrCardID` (already present), `groupSize`, and the ranked
candidates (the whole group for `ocr+vision`). `CandidateRanker`'s OCR reordering and `needsOCR` are
removed.

### Data the app bundles

- `catalog.json`: every printing (printingId, cardId, name, set, kind, rarity, artUrl). Generated by
  `fetch_cards.py` from the API cache (it already writes `catalog_full.json` to `datasets/processed/`).
- Full-catalog index: `printings.f32` + `printings.meta.json` covering all printings (~4k rows).
- The roster files (`roster.json`, `cards.json`, `printings.json`, `variants.json`) keep their role:
  they decide which printings have a character to spawn.

### UI

- Roster printing: the best guess spawns immediately, as today.
- Non-roster printing: a card-info panel (name, code, set, kind, rarity), with no spawn.
- Either way: a strip reading "OP05-119 · 4 printings" with the pick highlighted. Tapping it opens the
  group list (replaces "Not this one?"). Each row can be confirmed (✓) or chosen as the correct printing.
  "None of these" opens the manual picker.
- Thumbnails in the group list load on demand from `artUrl` and are cached on disk. Offline, the rows show
  text only (kind, rarity, set). Recognition itself never needs the network.
- Settings gets a **debug overlay** toggle (off by default): detected quad, OCR read, `method`, and
  similarity scores drawn live. It's used for the demo video.

## 2. Labels, dataset, and training

### Scan logs

`ScanRecord` gains `method`, `groupSize`, and `label` (`confirmed` | `corrected` | `none`). A confirm
tap sets `confirmed`. Choosing another printing sets `corrected` and `finalPrintingID`. Everything
else stays `none`. `dataset.scan_records` uses only `confirmed` and `corrected` scans. The existing
weak-label behavior (untouched scans counted as correct) is removed.

### Split and frozen test sets

- `split(printingId)` = stable hash of the printing ID → `train` (70%) or `test` (30%). It replaces
  the per-scan hash in `dataset.scan_split`.
- A test printing's real scans are never used for training, at any time.
- `make freeze-test` creates `test-vN` once the unfrozen test pool has ≥200 labeled scans across
  ≥30 printings. It refuses otherwise and prints the progress. It writes
  `ml/testsets/test-vN.json` (scan IDs, printing IDs, freeze date), which is **tracked in git**.
- Scans of test printings that arrive after a freeze go to the pool for `test-v(N+1)`, never into
  training and never into an existing frozen set.
- Synthetic images and negatives stay as secondary diagnostics. The headline metrics come from the
  latest frozen real test set.

### Metrics

Computed by `evaluate.py` through `cardvision match`, each with a 95% Wilson confidence interval:

- **OCR accuracy**: the parsed code equals the true code (over all detected test scans).
- **Within-group accuracy**: correct printing given a correct code with a group of ≥2 (the vision
  model's job).
- **End-to-end top-1**: the final printing equals the label (over all test scans).
- Everything is broken down by `method`, plus the existing detection, per-condition, and rejection tables.

### Training (`train_embedding.py`)

- Classes: all catalog printings. Views: `synth.augment_card` on catalog art, plus the real scans
  from train-split printings, oversampled (weight configurable, default 4×).
- **Group-aware batches:** each batch includes whole same-code groups, so CosFace separates siblings
  such as base vs alt art.
- Output: MobileNetV3 embedder → Core ML `CardEmbedder.mlpackage`, backend ID
  `coreml:CardEmbedder@vN`.

### Model registry (Mac mini, gitignored except as noted)

`ml/models/vN/`: `CardEmbedder.mlpackage`, full-catalog index built with it, `metrics.json`, and
`MODEL_CARD.md`. The model card holds the parent version, date, training data counts (catalog
printings, real scans), test-set version, the three metrics with confidence intervals by `method`,
macOS and Xcode versions, and known caveats. `make ship` copies the card to `docs/models/vN.md`
(tracked) and the binaries to `ml/shipped/`.

## 3. Two-Mac workflow

| | MacBook | Mac mini |
| --- | --- | --- |
| Repo | clone | clone |
| `ml/datasets`, art, scans | none | all |
| Train / eval / showcase | — | yes |
| Build app | yes | no |

Git carries code, `results.csv`, `ml/testsets/*.json`, `docs/models/*.md`, and the chart SVG. rsync
carries `ml/shipped/` (mlpackage, index, `catalog.json`).

### Mac mini one-time setup (checked by `make mini-doctor`)

1. Xcode, the same version as the MacBook. Both Macs on the same macOS major version (Vision output
   can differ across OS versions, and model cards record the versions).
2. `uv`, then `make ml-setup` with the `train` extra.
3. File Sharing on, sharing `~/oplab-inbox`.
4. Remote Login on, with the MacBook's SSH key authorized.

MacBook: `ml/remote.env` (gitignored) with `MINI_HOST` and `MINI_REPO`.

### Make targets

| Where | Target | Behavior |
| --- | --- | --- |
| mini | `mini-doctor` | checks the setup items above and prints what's missing |
| mini | `import-scans` | imports new scan folders from `~/oplab-inbox` (skipping known IDs), moves originals to `~/oplab-inbox/imported/` |
| mini | `status` | new labels since the last shipped model, test pool progress (x/200 scans, y/30 printings), current shipped version |
| mini | `freeze-test` | freezes `test-vN` when the thresholds are met |
| mini | `train NAME=vN` | fine-tunes under `caffeinate -i` |
| mini | `eval NAME=vN` | evaluates on the latest frozen test set, writes `metrics.json` and `MODEL_CARD.md` |
| mini | `ship NAME=vN` | refuses unless vN was evaluated on the current frozen test set; copies to `ml/shipped/` and `docs/models/`, appends to `results.csv`, regenerates the showcase |
| mini | `showcase` | regenerates the chart, the case-study tables, and the static site; `PUBLISH=1` pushes the site |
| MacBook | `pull-model` | rsyncs `ml/shipped/` into the app resources; fails if the mlpackage version doesn't match the index `backend` |
| MacBook | `train-remote NAME=vN` | runs `make train` on the mini over SSH inside `tmux` |

The iPhone → mini step is manual: in the Files app, connect to `smb://<mini>.local`, then copy
On My iPhone → OnePieceAR → Scans into `oplab-inbox`.

The existing Vision feature-print baseline is recorded as `v0` on the first frozen test set, so the
chart starts from it.

## 4. Showcase

- `docs/ml-case-study.md`: hand-written narrative (problem, pipeline diagram, data and split rationale,
  eval method, results). Result tables live between generated markers that `make showcase` rewrites.
- `docs/models/vN.md`: generated model cards.
- `docs/img/accuracy.svg`: the three metrics per shipped version, with CI error bars, one series per
  frozen test set. The x-axis shows the version and its real-label count. Referenced by the README and the site.
- Static site (`ml/site/`, gitignored build output): the chart, a version table linking to the model
  cards, and test-set descriptions. `make showcase PUBLISH=1` pushes it to the public
  `op-tcg-ar-results` repo, which serves it with GitHub Pages.
- Demo video: recorded manually with the debug overlay on.
- **IP guardrail:** the site, charts, and committed docs contain no card art or scan crops. The
  showcase build fails if any file from `ml/datasets/`, `data/cards/art/`, or an image with card
  dimensions ends up in the output.

## Error handling

- OCR returns a code that isn't in the catalog → treated as no code (vision-only fallback). The scan
  log keeps the raw OCR read so misreads can be analyzed.
- Index/model mismatch on the device → existing behavior (ignore the index). `pull-model` prevents it
  at build time.
- The catalog is missing from the bundle → the app falls back to roster-only recognition and logs a warning.
- `import-scans` skips malformed folders (missing `scan.json` or `crop.jpg`), reports them, and leaves
  them in the inbox.
- `freeze-test`, `ship`, and `showcase` refuse rather than degrade: each prints the unmet condition.

## Testing

- `OnePieceKit` / `CardVision` unit tests: code lookup, restricted index search, the group-of-1
  shortcut, OCR-rotation fallback, the vision-only fallback threshold, and `method` assignment,
  including real Vision OCR on rendered synthetic cards.
- `RepoDataTests`: `catalog.json` decodes, and every roster printing exists in the catalog.
- ML lab `pytest`: printing-level split stability and no train/test overlap, freeze thresholds,
  frozen sets not changing on re-import, label filtering, Wilson intervals, the model-card generator,
  `ship` refusal conditions, and the showcase IP guardrail.
- Manual: the end-to-end loop on real hardware (scan → SMB → import → train → eval → ship → pull → build).

## Delivery order

Each phase is usable on its own:

1. **Catalog and code-first recognition**: `catalog.json`, full-catalog index, new `CardRecognizer`
   flow, CLI plus eval metrics by `method`.
2. **App UX and labels**: group strip and list, confirm/correct, info panel, thumbnails, `ScanRecord`
   fields, debug overlay.
3. **Dataset discipline**: printing-level split, label filtering, `freeze-test`, Wilson intervals, `v0`
   baseline.
4. **Two-Mac tooling**: `mini-doctor`, `import-scans` from the inbox, `status`, `pull-model`,
   `train-remote`.
5. **Training and registry**: group-aware batches, real-scan oversampling, model cards, `ship`.
6. **Showcase**: case study, chart, static site, publishing to `op-tcg-ar-results`.

## Out of scope

- A local VLM labeling assistant (possible later chapter).
- A separate verifier model (approach C). Revisit if within-group accuracy plateaus.
- Checking neighboring codes on OCR misreads.
- Any server or cloud processing of scans.
- Bundling card art for the full catalog.
